# 후보 선정과 데이터 정리

[프로젝트 소개](../README.md)

## 1. 제공 데이터와 서비스에 필요한 데이터를 구분했다

AI Hub 낚시성 기사 탐지 데이터의 Part1을 중심으로 복지 기사 후보를 탐색했다. 경제·정치·사회 분야의 Training·Validation 자료와 Clickbait_Auto·Clickbait_Direct·NonClickbait_Auto 유형을 대상으로 했다.

제공 데이터에는 제목·본문과 낚시성 라벨이 있었지만, 특정 복지 제도와 다섯 조건의 비교 기준 답안은 별도로 준비해야 했다. 나는 본문 담당 후보 검토와 최종 자료 정리에 참여했다.

| 필드 | 활용 목적 |
| --- | --- |
| `sourceDataInfo.newsID` | 기사 식별 및 검토표 연결 |
| `labeledDataInfo.newTitle` | 시험에 사용할 가공 제목 |
| `sourceDataInfo.newsContent` | 제목과 비교할 대응 본문 |
| `sourceDataInfo.newsTitle` | 참고용 원제목 |
| `labeledDataInfo.clickbaitClass` | 제공 데이터의 낚시성 라벨 |

가공 제목과 원제목을 구분했다. 입력을 원제목으로 바꾸면 제공 자료에서 구성한 제목·본문의 관계가 달라질 수 있기 때문이다.

## 2. 키워드 검색 후 서비스 범위를 검토했다

초기에는 ‘지원금·급여·생계’를 제목과 본문에서 각각 검색했다. 원본의 Training·Validation을 나눠 세 키워드 × 두 필드 × 두 분할의 12개 조합을 정리했다.

검색 결과에 단어가 있다는 것만으로 서비스에 적합하지는 않았다. ‘급여’에는 임금·퇴직급여가 포함됐고, ‘지원금’에는 기업·고용 지원 등 여러 제도가 섞여 있었다.

규칙·AI 기반 사전 분류로 후보·보류·제외와 근거를 정리하고, 데이터 담당자가 후보와 보류 및 범위가 쟁점인 기사의 원문을 확인했다. 처리 도구와 코드 작성에는 AI 지원을 활용했으며, 검색 조건·검토 기준과 최종 선정 판단을 구분해 작업했다.

### 초기 검색 목록의 규모

| 구분 | 건수 | 의미 |
| --- | ---: | --- |
| 제목 검색의 고유 후보 | 722 | 사회 분야 누락분을 보완한 뒤의 고유 기사 수 |
| 본문 검색의 고유 후보 | 6,599 | 키워드별 중복 기재를 제외한 고유 원본 후보 |
| 제목·본문 목록의 공통 기사 | 493 | 두 목록에 함께 포함된 고유 기사 |
| 초기 고유 탐색 목록 | 6,828 | 722 + 6,599 − 493 |

초기 본문 및 추가 탐색에서 프로그램이 검색한 원본 JSON은 155,851개였다. 위 수치들은 검색 규모이며 사람이 모든 기사를 정독한 수나 최종 사용 자료 수가 아니다.

### 실제 범위 검토에서 고민한 질문

| 사례 | 검토한 질문 |
| --- | --- |
| 특정 인물의 복지 신청 | 지원 조건을 설명하는 기사인가, 인물에 대한 반응이 중심인가? |
| 선정 기준 개선 권고 | 아직 지급 단계가 아니어도 대상·확정성 비교에 활용할 수 있는가? |
| 지자체의 보편적 지원 | 정의한 서비스의 지원 대상과 목적에 맞는가? |
| 코로나19 관련 지원 | 이름보다 실제 제도의 생활 안정·고용·사업 지원 성격을 구분해야 하는가? |
| 제목과 본문이 무관한 입력 | 일반 후보와 별도로 오류 탐지 상황을 살펴볼 자료인가? |

범위는 사례를 보며 구체화했다. 제도 이름만으로 모든 포함·제외를 결정하기는 어려웠고, 일부 정책 구분에는 추가 판단이 남았다.

## 3. 후보가 부족해 추가 검색을 진행했다

검색량은 많았지만 목적에 맞는 후보를 좁히자 사용할 수 있는 자료가 적었다. 관련 제도와 기관 용어로 검색을 확장하고 기존 목록과 중복을 비교했다.

| 추가 탐색 | 검색 일치 | 기존 목록 등과 중복 | 새 검토 목록 | 최종 자료에 신규 반영 |
| --- | ---: | ---: | ---: | ---: |
| 기초생활보장·기초수급 | 195 | 98 | 97 | 1 |
| 정책·기관·직군 및 문맥어 확장 | 16,705 | 3,779 | 12,926 | 0 |

두 번째 탐색에서는 구체적인 제도명과 일반적인 대상·기관 용어를 구분했다. 일반어는 복지·생활안정·지원금 등의 문맥어와 함께 나타날 때 수집하는 방식이었다. 12,926건 역시 새 검색 목록의 규모로, 사람이 전부 읽었다는 의미는 아니다.

첫 추가 검색에서는 제도 개선 권고 기사 1건이 반영됐고, 이후 확장 검색에서는 최종 추가 자료가 없었다. 이 경험을 통해 검색 범위를 넓히는 것과 과업에 적합한 자료를 확보하는 것은 별도로 살펴야 한다는 점을 배웠다.

## 4. 중복을 판단할 단위를 나눴다

| 기준 | 확인하려는 문제 |
| --- | --- |
| 원본 폴더·파일키 | 같은 파일이 여러 키워드 검색에 반복 포함됐는가? |
| 기사 ID | 제목 담당과 본문 담당이 같은 기사를 선정했는가? |
| 정규화한 본문 | 본문은 같지만 제목이 다른 입력인가? |
| 제목·본문 쌍 | 실제 시험 입력이 완전히 같은가? |

본문이 같아도 제목이 다르면 다른 비교 사례가 될 수 있어, 본문 중복만으로 무조건 삭제하지 않았다. 원본 경로와 해시를 함께 관리해 검토표의 항목을 원본 JSON에 연결했다.

해시·문자열 기준의 중복 대조는 같은 사건을 다룬 유사 기사 전체를 찾아내는 것과는 다르다. 원본 단위, 본문 단위, 입력 쌍 단위를 구분하는 데 초점을 맞췄다.

## 5. 최종 자료를 구성하고 전달했다

본문 담당 후보 33건과 제목 담당 고유 후보 21건을 통합할 때 공통 기사 9건을 확인했다. 통합 후보는 45건이었고, 최종 확정 목록에서는 44건이 남았다. 이 차이 1건의 개별 제외 이유는 현재 기록만으로 확정하지 않았다.

| 최종 묶음 | 건수 | 용도 |
| --- | ---: | --- |
| 사용가능후보 | 44 | 다섯 조건의 사람 라벨 작성과 결과 대조 |
| 경계시험용 | 13 | 범위·입력 결함 등 경계 상황 관찰 |
| 합계 | 57 | 모델링 담당자에게 전달한 기사 묶음 |

‘사용가능후보’는 모두 정상 기사라는 뜻이 아니다. 경계시험용 13건에는 같은 다섯 조건의 사람 라벨을 작성하지 않았으며, 별도 독립 평가 세트로 분리한 것도 아니다.

최종 원본 JSON을 먼저 전달하고 이후 라벨을 연계했다. 기사 ID와 원본 연결 정보를 유지해 데이터 담당자의 검토와 엔지니어의 입력이 같은 자료를 가리키도록 정리했다.

## 6. 데이터 제약이 서비스 설계에 영향을 줬다

### 발행일이 없었다

최종 57건의 원본에는 기사 발행일 필드가 없었다. 제목의 ‘10월’과 본문의 ‘다음 달’이 같은 시점인지, 신청 마감을 절대 날짜로 계산할 수 있는지 판단하는 데 제약이 생겼다. 파일 생성일이나 기사 ID를 발행일로 대체하지 않았다.

이 제약은 팀이 계획한 마감 기반 검수 우선순위를 본선 구현 범위에서 제외하는 배경 중 하나가 됐다.

### 원본 분할과 실제 평가 분할은 달랐다

최종 자료의 원본 출처는 Training 49건·Validation 8건이었지만, 팀은 57건 모두를 반복 개발에 활용했다. 따라서 원본 폴더의 이름만으로 학습용과 독립 평가용이 분리됐다고 설명할 수 없었다.

## 7. 배운 점

데이터가 많다는 사실만으로 원하는 분석이나 평가가 가능한 것은 아니었다. 검색 조건, 포함 범위, 중복 단위, 원본과의 연결이 모두 서비스 질문과 맞아야 했다.

특히 데이터의 한계는 뒤늦게 적는 주의사항에 그치지 않았다. 기사 발행일의 부재처럼 실제 기능 범위를 결정하는 근거가 되기도 했다.
