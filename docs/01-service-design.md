# 서비스 기획: 오류·정보 지연·검수 부담을 함께 고려하다

[프로젝트 소개](../README.md)

이 문서는 팀의 예선 설계와 본선에서의 변경을 정리했다. 선택의 이유는 남아 있는 설계와 논의를 바탕으로 재구성했으며, 팀의 기획을 개인의 단독 성과로 기술하지 않았다. 개인의 데이터 작업과 제안은 별도 문서에서 설명한다.

## 1. 정보 신뢰성에서 제목·본문 비교로 범위를 좁혔다

초기 문제의식은 저품질·불신뢰 정보를 줄이는 것이었다. 그러나 정보의 신뢰성에는 사실 여부, 출처, 선정성, 표현 왜곡 등 서로 다른 질문이 섞여 있었다.

팀은 입력과 비교 대상을 정의하기 위해 ‘복지 기사 제목의 지원 조건이 같은 기사의 본문으로 뒷받침되는가’에 집중했다. 초기 범위에 있던 소개문 관련 작업은 제외하고, 생활안정지원금·생계급여 관련 기사 검토를 우선했다.

복지 기사에서는 대상 제한이나 금액의 상한, 신청 시점, 정책 단계의 차이가 독자의 다음 행동에 영향을 줄 수 있다. 동시에 반복적으로 나타나는 조건을 정해 검토 질문을 구체화할 수 있었다. 다만 본선에서 실제 자료를 찾아보니, 제공 데이터의 전체 규모와 서비스에 적합한 기사의 규모에는 큰 차이가 있었다.

## 2. 직접 사용자를 기사 검수자로 정했다

독자는 잘못된 정보를 접할 수 있는 영향 대상이고, 검수자는 제목·본문을 확인한 뒤 수정 요청이나 게시 여부 등 후속 판단에 참여하는 업무 주체다. 팀은 기사 검수자와 플랫폼 운영자를 직접 사용자로 상정했다.

그에 따라 출력도 기사에 대한 긴 설명보다 검수자가 확인할 조건·원문 구절·위치·사유를 중심으로 구상했다. AI 결과를 받은 사람이 어디를 보고 무엇을 판단해야 하는지 명확하게 하는 것이 목적이었다.

## 3. 다섯 조건으로 비교 질문을 구체화했다

| 조건 | 비교할 질문 | 구분할 사례 |
| --- | --- | --- |
| 대상 | 누가 지원받으며 어떤 자격 제한이 있는가? | 전체 가구 / 특정 자격의 가구 |
| 금액 | 얼마이며 상한·단위·주기가 같은가? | 최대액 / 정액, 가구당 금액 / 총사업비 |
| 지역 | 지원 사업의 적용 지역이 같은가? | 특정 지역 사업 / 전국 사업 |
| 기간 | 어떤 종류의 시간 조건을 말하는가? | 신청 / 지급 / 사용 / 기준 적용 기간 |
| 확정성 | 정책이 어느 단계에 있는가? | 권고 / 발의 / 심의 / 결정 / 시행 |

기존의 낚시성 여부만으로는 검수자가 확인해야 할 조건을 구분하기 어려웠다. 다섯 조건을 나누면 판정이 달라지는 이유와 모델이 놓치는 내용을 더 구체적으로 살펴볼 수 있었다.

미래 일정이 있다고 미확정인 것은 아니다. 이미 결정된 지원의 다음 달 지급과, 아직 심의 중인 지원의 지급 예정은 다르다. 숫자나 단어의 일치보다 같은 사업·대상·단위·시점을 비교하는지가 중요했다.

## 4. 판단 근거를 원문에 연결하려 했다

검수자가 AI의 설명만 믿지 않고 확인할 수 있도록 제목의 주장과 본문의 대응 구절·위치를 함께 제시하려 했다.

여기에는 두 가지 질문이 있었다.

1. 인용한 문장이 실제 원문에 존재하는가?
2. 그 문장이 제목의 주장을 의미상 뒷받침하는가?

원문에 있는 문장이라도 다른 사업의 금액이나 다른 종류의 기간을 설명할 수 있다. 인용의 존재와 근거의 적절성을 구분해야 했다. 본선에서는 모델이 자유롭게 설명을 생성하기보다 정해진 구절·문장·값을 선택하는 방식으로 구현 방향을 조정했다.

## 5. 비교 결과를 후속 처리와 연결하려 했다

예선에서는 다음 세 경로를 구상했다. 아래는 목표 설계이며 현재 구현 전체를 나타내지 않는다.

| 경로 | 설계한 역할 | 사람의 개입 |
| --- | --- | --- |
| A · 조건부 자동 통과 | 정한 조건을 만족한 기사 처리 | 기준 설정, 사후 점검, 필요 시 중단 |
| B · 사전 사람 검토 | 중요 조건 충돌 등 의심 사례 확인 | 원문 확인 후 후속 조치 판단 |
| C · 보류 | 입력 결함·장애 등으로 판단이 어려운 상태 관리 | 원인 확인과 입력 보완 |

조건별 의미 판정과 처리 경로는 서로 다른 결정이다. ‘차이’가 있다는 사실을 기록한 뒤, 그 영향과 운영 여건을 고려해 사람이 볼지 정하는 구조를 생각했다.

## 6. 모든 기사를 사람이 보는 방식의 부담을 고려했다

사람 검토를 확대하면 오류를 확인할 기회가 늘지만, 검수량과 대기시간도 늘어날 수 있다. 정상적인 복지 정보의 전달이 늦어지는 문제와 시간 압박 속 형식적으로 승인하는 문제도 함께 고려했다.

| 선택 | 줄이려는 문제 | 함께 고려할 부담 |
| --- | --- | --- |
| 자동 통과 축소 | 잘못된 조건의 기사 노출 | 사람 검토 적체와 정보 지연 |
| 사람 검토 확대 | AI가 놓친 오류 | 피로, 시간 압박, AI 설명에 대한 과도한 의존 |
| 보류 확대 | 판단 근거가 부족한 처리 | 필요한 정보의 장기 미전달 |
| 자동 통과 확대 | 대기시간과 수작업 | 오류 확산과 독자의 오해 |

### 검토 용량을 계산한 설계 예시

예선에서는 아래 가정으로 처리 여력을 계산했다. 실제 유입 로그나 검수 시간 측정값이 아닌 설계용 가정이다.

| 항목 | 가정 또는 계산 |
| --- | --- |
| 일별 유입 | 100건 |
| 검수 인원과 배정 시간 | 2명 × 120분 = 240분 |
| 과업당 평균 시간 | 5분 |
| 일별 처리 가능량 | 240 ÷ 5 = 48과업 |
| 자동 통과 50%일 때 나머지 과업 | 50과업 |
| 자동 통과 기사 중 20% 사후 점검 | 50 × 20% = 10과업 |
| 예상 검토량 | 60과업 |
| 처리 가능량 초과분 | 하루 12과업 |

단순히 절반을 자동 처리한다고 가정해도 검토량은 처리 여력을 넘었다. 신고·재작업까지 포함하면 더 많은 여력이 필요할 수 있었다. 자동화 비율뿐 아니라 사람이 감당할 수 있는 업무량을 함께 봐야 한다는 설계상의 근거였다.

## 7. 검토 순서와 인간 감독까지 생각했다

검토 요청을 보냈더라도 사람이 필요한 시점에 확인하지 못하면 조치가 늦어진다. 그래서 신청 등 시간 조건과 대기시간을 고려하는 우선순위를 계획했다. 마감을 알 수 없는 기사를 중요하지 않다고 취급하거나, 급한 기사 때문에 다른 기사가 계속 밀리는 문제도 살폈다.

검토 순서를 바꾸는 것만으로 전체 처리 용량이 늘어나지는 않는다. 인력과 유입량, 장애 대응도 함께 고려해야 했다.

인간 감독 역시 건별 승인뿐 아니라 자동 통과 결과의 사후 점검, 자동화 범위 설정, 중단·재개 권한까지 포함해 생각했다. 검수자가 원문을 열거나 승인했다는 기록과 실제로 오류를 교정했다는 결과를 구분하고자 했다. 사람의 판단 변화와 소요 시간을 확인하는 시험은 기획했지만 아직 수행하지 않았다.

## 8. 본선에서 구현 범위를 조정했다

2026-11-19 기준 팀 보고를 바탕으로 정리했다.

| 항목 | 예선의 목표 | 본선의 현재 상태 |
| --- | --- | --- |
| 조건 비교 | 다섯 조건의 의미와 근거 비교 | 모델이 구절·문장·값을 선택하고 프로그램이 비교. 값 비교는 금액·기간·지역 중심 |
| 대상·확정성 | 의미 차이 판정 | 현재 채택 구성에서는 직접 비교하지 않음 |
| 처리 경로 | A 자동 통과 / B 사람 검토 / C 보류 | 자동 게재 / 사람 검토 두 경로를 오프라인 기록 |
| 우선순위 | 마감·대기시간 고려 | 발행일 등 근거 부족으로 범위 제외 |
| 평가 자료 | 개발과 독립 평가 분리 | 최종 57건이 반복 개발에 사용됨 |
| 인간 감독 효과 | 실제 오류 교정·시간 관찰 | 실제 검수자의 판단·시간을 수집하는 시험은 미완료 |
| 서비스 운영 | 조건 충족 후 외부 게시 | 실제 게시 없이 오프라인 시험 |

기획을 구현으로 옮기면서 데이터와 모델의 제약이 구체적으로 드러났다. 따라서 초기 목표와 현재 기능을 나누고, 아직 확인하지 못한 효과를 운영 성과로 제시하지 않았다.
